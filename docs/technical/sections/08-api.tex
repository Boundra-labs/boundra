\chapter{API and sessions}\label{ch:api}

The API is a NestJS application under \code{/api/v1}. The machine-readable contract lives in \code{docs/openapi.json}; outside production, Swagger UI shows it at \code{/api/docs}. It never holds keys: everything that changes the chain is a transaction the owner signs.

\begin{itemize}
  \item The challenge is an EIP-4361 (SIWE) message bound to the web origin, chain 84532 and a single-use nonce that expires after 5 minutes. The web app refuses to ask for a signature if the message names another origin.
  \item Verification sets the \code{\_\_Host-boundra\_session} cookie (HttpOnly, Secure, SameSite=Strict, 12 hours) and returns a CSRF token.
  \item Every \code{POST} and \code{PATCH} needs the \code{Origin} header equal to \code{WEB\_ORIGIN} and the \code{X-CSRF-Token} header.
  \item The owner is always taken from the session. Addresses in request bodies are never used for authorization, and another owner's resources return \code{404}.
  \item Bodies are limited to 16 KB; sign-in routes allow 10 requests a minute per client, other routes 120.
\end{itemize}

\section{API tokens for apps and assistants}

Apps built with the SDK and AI assistants using the MCP server sign in with an \emph{API token} instead of the cookie:

\begin{enumerate}
  \item \code{POST /auth/challenge \{address, client: "token"\}} returns a SIWE message whose statement tells the owner exactly what they grant: the token can read the account and prepare mandates for review, and cannot approve anything, sign transactions or move funds.
  \item The owner's wallet signs it. Verification returns the token and sets no cookie. The signed statement decides the session kind, so an altered statement is rejected.
  \item Clients send \code{Authorization: Bearer <token>}. No CSRF token is needed, since browsers never attach this header on their own, and CORS still admits only the web origin.
\end{enumerate}

Tokens and cookies are never interchangeable, admin routes need the admin's browser session, and tokens are listed and revoked from the web app (\code{GET /auth/tokens}, \code{POST /auth/tokens/:id/revoke}, browser session only). Only token hashes are stored.

\section{Errors and health}

Errors have one shape, with a stable \code{code}, a message and a recovery hint; internals are never echoed.

\begin{lstlisting}
{ "error": { "code": "STALE_PREVIEW",
             "message": "...",
             "recovery": "Reload the latest preview and review it again." } }
\end{lstlisting}

{\raggedright Codes include \code{UNAUTHENTICATED}, \code{CSRF\_REJECTED}, \code{RATE\_LIMITED}, \code{VALIDATION\_FAILED}, \code{CHALLENGE\_INVALID}, \code{WRONG\_CHAIN}, \code{INSUFFICIENT\_BALANCE}, \code{STALE\_PREVIEW}, \code{INVALID\_STATE} and \code{DEPENDENCY\_UNAVAILABLE}.\par}

\code{GET /health/live} answers when the process is up; \code{GET /health/ready} also reports PostgreSQL, a fresh worker heartbeat and the worker's mode. The web app's \code{/status} combines this with the web release for monitoring.
